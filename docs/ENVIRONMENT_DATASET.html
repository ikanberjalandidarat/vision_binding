Eight diverse Minecraft environments — dataset v2

Build → record → generate GIFs and overview maps on Oscar → export review bundle → user review. No model extraction, probes or navigation training is launched.

Some early v2 runs finished their routes while using obsolete Minecraft block IDs for walls, trees, fences or buildings. Treat those recordings as exploratory only. These are deterministic authored scenes in Minecraft, including the forest, mine and village. They are not claimed to be untouched vanilla-generated biomes or villages. This first review set has one world per category. We will judge appearance from the real GIFs, then revise before treating it as a frozen dataset.

What is standardized?

33×33-block build footprint; seed 731; 448×280 RGB; fixed time/weather; vegetation decay disabled; two recording routes per environment; initial heading scan; capture every eight simulation ticks; two ticks per action; full pose, action and image-hash metadata. Routes visit common spatial anchor requests in different orders, with collision-aware grid paths appropriate to each world. Start positions, lighting and elevations are documented and may differ by category. Route lengths are not forced equal.

The controller is scripted and uses simulator pose, not a learned model. It can issue jump actions for upward steps. It rejects out-of-bounds poses and stops if a waypoint does not advance for 400 ticks. Failures keep partial frame/pose metadata; completion is not faked. Planned routes avoid solid cells and height changes larger than one block.

Review outputs

  • Sixteen first-person GIFs: two per environment.
  • all-eight.gif: eight-panel montage, synchronized by simulation time at 4× playback. Shorter recordings hold their final frame.
  • Top-down build maps alongside the GIFs, with world axes, start positions and measured paths.
  • Separate ground-elevation maps for every world, especially hills. Roofs/canopies are hidden in plan views.
  • index.html and summary.json, explicitly awaiting user review.

Overview maps come from the construction specification; they are not aerial Minecraft screenshots, learned representations or proof that every command executed. Actual first-person images are the rendering evidence. GIF filenames appear beneath the GIFs.

Submit on Oscar

After committing/pushing the changes yourself and pulling on Oscar, run the following in a fresh output directory. The first four cover the room floor, outdoor hedge maze, forest, and village: the scenes most affected by the old block IDs. Their pilot gallery is a visual gate before collecting the other four. A fresh run is required after block-ID changes, including for previously completed routes.

(
set -e
cd ~/projects/zef-binding
mkdir -p logs
export MC_RENDER_PYTHON="/oscar/scratch/$USER/zef-binding/envs/render-spatial/bin/python"
dataset_root="/oscar/scratch/$USER/zef-binding/runs/diverse-dataset-v2-$(date +%Y%m%d-%H%M%S)"
pilot=$(sbatch --parsable --array=0,3,4,7%2 scripts/slurm/diverse_dataset.sbatch "$dataset_root" collect)
pilot_gallery=$(sbatch --parsable --dependency=afterok:"$pilot" --kill-on-invalid-dep=yes scripts/slurm/diverse_dataset.sbatch "$dataset_root" gallery 0,3,4,7)
printf 'Dataset: %s\nPilot: %s\nPilot gallery: %s\n' "$dataset_root" "$pilot" "$pilot_gallery"
)

Review pilot-review/index.html and the actual GIFs. A completed route does not prove that its landmarks appeared. Once the four scenes look right, submit the other four:

root="/oscar/scratch/$USER/zef-binding/runs/REPLACE_WITH_DIVERSE_DATASET_DIRECTORY"
rest=$(sbatch --parsable --array=1,2,5,6%2 scripts/slurm/diverse_dataset.sbatch "$root" collect)
gallery=$(sbatch --parsable --dependency=afterok:"$rest" --kill-on-invalid-dep=yes scripts/slurm/diverse_dataset.sbatch "$root" gallery)
printf 'Remaining: %s\nFinal gallery: %s\n' "$rest" "$gallery"

The final gallery requires all eight environments and both complete routes in each, with specifications matching the current code. It stops at review; no model jobs follow it.
